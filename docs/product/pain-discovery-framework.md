# Pain Discovery Framework — SaaS Pipeline OS

## Core rule

Do not build until target segment and concrete pain are explicit.

## Pain statement format

```text
For [concrete target group],
who regularly [specific context],
[concrete pain] is a problem
because it causes [measurable consequence].
Today they solve it with [current workaround],
but that is insufficient because [gap].
```

## Scoring criteria

| Criterion | Meaning | Weight |
|---|---|---:|
| Frequency | How often does it occur? | 20% |
| Intensity | How painful/costly is it? | 25% |
| Willingness to pay | Would someone pay or switch? | 20% |
| Reachability | Can we reach users directly? | 15% |
| MVP feasibility | Can we solve a slice quickly? | 10% |
| Differentiation | Is the angle meaningfully different? | 10% |

## Decision rule

- Score ≥ 4.0: validate with users.
- Score 3.0–3.9: sharpen.
- Score < 3.0: park.

## Weak signals

- Likes.
- Friendly feedback.
- “Sounds interesting.”
- “I might use this.”
- Generic feature wishes.
- Broad target groups.

## Strong signals

- Concrete recent incident.
- Existing workaround.
- Time/money already spent.
- User asks for access.
- User shares screenshots/data.
- User complains about missing functionality.
- User returns repeatedly.
